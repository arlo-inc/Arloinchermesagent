# Keep List and Recommendation

This decision surface is based on read-only inspection of OpenClaw `v2026.4.29` and Hermes main at `5d3be898a8671eb9fb99cf18f43165502f54e7f4`. "Winner" means "best substrate to lift or emulate for Charlie Phase 2," not "ship unchanged."

## Concern Decisions

## Top-Level Recommendation

Charlie's Phase 2 substrate should be a hybrid, with Hermes as the agent-behavior core and OpenClaw as the integration/control-plane donor.

Recommended Charlie composition:

1. Hermes-derived core for memory provider lifecycle, skills loop, Kanban, subagent delegation, context compression behavior, session SQLite/FTS, MCP client, and compact event hooks.
2. OpenClaw-derived substrate for multi-platform gateway, cron scheduler, voice/speech routing, dashboard/control UI concepts, and broad provider routing.
3. Arlo-authored prompt assembly, tenant authority boundary, capability registry, policy hooks, and tenant-aware storage wrappers.

The lift plan that also benefits the existing platform tenant:

1. Define an Arlo substrate adapter contract around the 15 concerns before importing runtime code. The first adapter should wrap Hermes session/memory/skills/Kanban with explicit `tenant_id`, `agent_id`, `session_id`, `authority_grant_id`, and `workspace_id`.
2. Stand up Charlie on a minimal Hermes-behavior lane: SQLite sessions, built-in memory plus one external memory provider stub or tenant-local provider, skills, Kanban, context compression, tool registry, and MCP client.
3. Add OpenClaw gateway/cron/provider pieces only through Arlo mediation: no direct channel dispatch to agent code until tenant resolution, allowlist, and authority binding are in place.
4. Reuse the same adapter contract for the existing platform tenant so Charlie is not a special-case fork. The platform tenant should get immediate benefit from Hermes session search/Kanban and OpenClaw cron/gateway hardening.

The combined stack is genuinely better than either alone if Arlo keeps the seam strict. Hermes alone gives Charlie agency, learning, durable work, and recall but lacks OpenClaw's integration breadth. OpenClaw alone gives breadth and operational surfaces but is less focused on self-improving agent behavior. Together they make sense only if Arlo authors the moat layer and treats both repos as replaceable substrate packages.

## Surprises

- The two repos already know about each other: OpenClaw has `migrate-hermes`, and Hermes has `hermes claw migrate`. This suggests the OpenClaw-Hermes bridge is not purely speculative; migration pressure already exists in both directions.
- Hermes's Kanban substrate is stronger than expected and is closer to a real durable multi-agent work queue than OpenClaw's task ledger.
- OpenClaw's integration count is real, not just README posture. The `extensions/` tree contains concrete channel/provider/tool directories for well over 50 integrations.
- OpenClaw's context-engine slot is cleaner than Hermes's pluggability, but Hermes's actual compressor is more production-useful. The best answer is not a pure winner; it is Hermes behavior behind an Arlo/OpenClaw-style slot.
- Neither repo can own Arlo prompt assembly. Both inject useful prompt blocks, but tenant authority and governance have to sit above them.
- Project-level plugins and skills are a hidden risk for multi-tenant deployment. They are useful for local agents, but Charlie should not load project substrate without an Arlo trust decision.
