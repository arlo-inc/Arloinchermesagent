# Phase 1 Closure

I committed three recon artifacts under `phase-1-recon/`: the OpenClaw inventory, the Hermes inventory, and the keep-list recommendation document. The main surprise is that the two repos already contain migration paths toward each other, which makes a combined substrate less hypothetical than the original posture implied. Hermes was stronger than expected on durable work coordination: its Kanban database, session SQLite/FTS, memory provider lifecycle, and skills loop are the most Charlie-shaped pieces found in either repo. OpenClaw was stronger than expected on operational breadth: the gateway, cron, provider matrix, voice stack, and integration directories are real and extensive.

Without standing up either substrate, I could not verify runtime health, actual gateway adapter behavior, dependency drift, live provider compatibility, dashboard polish, or whether the advertised integrations succeed past static registration. My Phase 2 recommendation is to stand up Charlie against the keep list using a strict Arlo-authored adapter layer: Hermes-derived agent behavior first, then OpenClaw-derived gateway/cron/provider/voice pieces only after tenant authority binding is in place. The first Phase 2 success criterion should be a tenant-scoped Charlie session with persistent session storage, memory, skills, Kanban delegation, context compression, and one safe message ingress path. The governor should decide before Phase 2 whether project-level plugins/skills are disabled by default, which memory provider Charlie should use first, and whether the first ingress path is CLI/TUI, web dashboard, or a single messaging channel. I recommend keeping dashboard and voice out of the first boot unless the VPS provisioning includes enough time for operator-console and audio permissions work.
